# Common Pitfalls & Best Practices

Scope: this file governs `packages/vue-stdout` only. The toolkit monorepo holds
many unrelated packages; nothing here is a repository-wide rule.

- AGENTS.md is the source of truth. CLAUDE.md is a symlink to it.
- Bug fixes must follow test-first: write the test that reproduces the bug, **run it and see it fail**, then fix the code and see it pass. A test that was never observed red proves nothing — it may be asserting something that was already true, or asserting nothing at all. The same rule applies to a claimed no-op: prove the "before" state before changing it.
- The test directory is `test/`, singular. Two homes, and the split is deliberate: unit tests sit **beside their target in `src/`** (`src/tree/layout.test.ts`, `src/input/parseKeypress.test.ts`), while behaviour, integration and cross-cutting tests live in `test/` (`test/use-focus.test.ts`, `test/parity/**`). `src/` is therefore *not* build-inputs-only here; `build.config.ts` bundles from explicit entries, so test files never reach `dist/`.
- Type-level tests are `*.test-d.*` and run in the same command: `pnpm test` is `vitest run --typecheck`. A type assertion is not a separate suite you can forget to run.
- Verify with `pnpm test`, `pnpm check-types` and `pnpm build`, in this package. The green baseline is **1173 tests / 77 files**, `check-types` and `build` both exit 0. `check-types` is two `vue-tsc --noEmit` passes — the library (`tsconfig.json`) and the package's own Node-side config files (`tsconfig.node.json`); it is `vue-tsc`, not `tsc`, because `.vue` fixtures exist. When a change can affect another workspace (a dependency version, the catalog, an example), also run root `pnpm check-types` and root `pnpm build`.
- Commit messages follow Conventional Commits with the package as scope: `fix(vue-stdout): ...`, `docs(vue-stdout): ...`, `chore(examples): ...`. A change to workspace-level plumbing takes no scope (`build: catalog tsx ...`).
- **Every commit builds and passes on its own.** Split a change by what keeps the tree green, never by area — "the source in one commit, the call sites in the next" reads tidy and leaves a commit that does not compile. When a rename or removal touches its own call sites, they belong in the *same* commit; the follow-up commits are the ones that only add. This branch has twice produced a red intermediate commit by splitting on area, and a history that cannot be bisected is worth less than a tidy-looking one.
- **Commits carry no agent attribution.** No `Co-Authored-By` trailer, no "Generated with" line, no tool name anywhere in the message. This is a standing instruction from the repository owner and overrides any tool default.
- Prefer promise chains (`.then()`) over `async`/`await` — a standing owner preference. Note that almost all of `src/` is synchronous by design (the render path must be, so `renderToString` can be); the one asynchronous module is `src/sfc/hook.ts`, whose `async` signature is imposed by Node's ESM loader contract.
- Reactivity: `shallowRef` by default. `ref()` is only used where the value is a primitive and depth is meaningless (`src/hooks/useBoxMetrics.ts`, `src/hooks/useContainerSize.ts`); a deep `reactive()` appears nowhere in `src/` and adding one needs a written justification. Shared registries use `shallowReactive` (`src/focus.ts`).
- Never hand out a writable ref whose write the runtime will silently ignore. Where the owning object has a setter and no read path, expose a **read-only** ref plus the method that writes (`FocusManager.activeFocusId`, `useBoxMetrics`/`useContainerSize` metrics, `useWindowSize`). A ref that reads back its own last write while the terminal shows something else is a lie, not an API.
- Shared terminal state gets **one** subscription, owned by `Container`, that composables derive from with `computed`. Never attach a listener per consumer: fifteen mounted components produced a real `MaxListenersExceededWarning` on stderr mid-frame, which garbles the very output this package exists to control. See [gotchas](.agents/docs/gotchas.md#per-consumer-stream-listeners-garble-the-frame).
- The DOM tree (`src/tree/DOMTree/**`) must stay non-reactive. It is rebuilt and re-measured by Yoga on every frame; making it reactive would put a proxy on the hot path for no observer.
- **SFC is the foundation; TSX/JSX is a supplementary feature** — the owner's words, 2026-08-30. Both stay supported; what this fixes is emphasis. New examples, README material and playground demos are `.vue` with `<script setup lang="ts">` unless there is a stated reason otherwise, and `playground/demos/layout.tsx` stays `.tsx` on purpose so the JSX path is compiled, type-checked and mounted on every run. Do not use it as licence to drop JSX support, stop type-checking `.tsx`, or remove `unplugin-vue-jsx` from a compile path. See [intent](.agents/docs/intent.md#the-authoring-surface).
- **`vue-tsc` passing is not evidence that a template prop arrives.** Volar checks a template against the *declared* prop types, and this catalog declares no runtime `props` at all, so the types and the runtime are two different things. Two forms used to type-check and paint nothing; both are fixed at the boundary where component props become host attributes, and both are kept fixed by a hand-written key list whose completeness is a type-level assertion, not a habit. A bare boolean attribute (`<Text bold>`) was the falsy empty string — `src/components/booleanProps.ts` casts it, so **adding a boolean prop to any component requires adding its name to `BOOLEAN_PROP_KEYS` and routing that component through `castBooleanProps`**. A kebab-case prop name (`<Box border-style="round">`) never reached the renderer at all, for every multi-word prop and not just booleans — `src/components/kebabProps.ts` rewrites it, so **adding a multi-word prop to `Styles`/`BoxProps`/`TextProps` requires adding its name to `KEBAB_PROP_KEYS`**, and giving `Transform`/`Static`/`NewLine` their first multi-word prop requires routing it through `camelizeProps`. All four requirements fail `pnpm test` when unmet. `camelizeProps` runs before `castBooleanProps`, because `<Text dim-color>` is both defects at once. Template whitespace condensing separately adds a leading/trailing space to multi-line text content and deletes a trailing whitespace-only node. All of it is in [gotchas](.agents/docs/gotchas.md#vue-tsc-passing-is-not-evidence-that-a-template-prop-arrives).
- `.tsx` needs a Vue JSX plugin (`@vitejs/plugin-vue-jsx` / `unplugin-vue-jsx`); `@andrew_l/vue-stdout/register` covers `.vue` only. **This package's own** `.tsx` compile paths — `vitest.config.ts` and `build.config.ts` — must additionally be handed `isCustomElement` from `src/sfc/compiler-options.ts`, because `NewLine.tsx` and several `.tsx` tests emit the private host tags. (`Box.tsx` and `Text.tsx` used to as well; they call `h()` now so that Vue does not wrap their slot children in a Fragment, which cost two host `DOMText` anchors per component — `test/component-host-tree.test.tsx` holds that, and it is the only thing that can, since the frame is byte-identical either way.) A consumer never needs it, and `examples/cli-vite/vite.config.ts` is the standing proof: stock `plugins: [vue(), vueJsx()]`, nothing configured. Do not export `isCustomElement` or reintroduce a preset that does. **Under Vite the JSX plugin must also keep `enforce: 'pre'`** (`enforcePre` in `vite.config.ts`): `unplugin-vue-jsx` declares no `enforce`, and Vite's built-in transform sits ahead of the normal plugin bucket, so without it Vite compiles the JSX itself through `vue/jsx-runtime` and `@vue/babel-plugin-jsx` never runs — dev and test then carry different JSX semantics from the shipped build, silently and with the suite green. `test/jsx-vite.test.tsx` asserts the compiled shape; see [gotchas](.agents/docs/gotchas.md#dev-and-build-compiled-jsx-with-different-semantics).
- **This package ships no compiler preset and no plugin wrappers.** It compiles its own sources with `unplugin-vue` and `unplugin-vue-jsx` (`vite.config.ts`, shared by `vitest.config.ts`; `build.config.ts` uses the `/rollup` build of the same JSX plugin) because both expose client output as a supported option, which the `@vitejs` pair does not. There is no server renderer here, so SSR-flavoured codegen throws on mount, and vitest with `environment: 'node'` drives Vite's SSR transform. Do not reintroduce `pinClientCodegen`/`forceClientTransform` or a `vueStdout()` preset that constructs someone else's plugin for the consumer: patching another package's hooks is what this arrangement replaced, and the second patch silently cost `.vue` source maps for three reviews. The prohibition is on presets and hook wrappers, not on the existence of a Vite-facing entry — `@andrew_l/vue-stdout/dev` is a dev server, configures no compiler, and is the one place in `src/` that may import `vite`. `test/sfc-source-maps.test.ts` is the guard — it reads a stack frame's source position, not the presence of a `.map`. The full argument and its measurements are in [gotchas](.agents/docs/gotchas.md#the-vue-plugins-that-needed-patching-and-the-ones-that-do-not).
- **The dev server runs the app in the dev server's own process, and its seam into the app is internal.** `@andrew_l/vue-stdout/dev` (`src/vite/**`) imports the entry into Vite's runnable `ssr` environment; a child process is rejected because two TTY-aware processes on one terminal corrupt each other's frames, and `Container.destroy()`'s restoration assumes a single owner. `src/dev/**` is the runtime half and stays **out of `exports` and out of `src/index.ts`** — it is a seam for our own plugin, not a consumer surface, and it is inert until a dev server connects. Two things there are not optional: the bridge state lives on `globalThis`, because the plugin's copy and the app's copy are two module instances in one process that must agree on who owns the terminal; and every `vite:*` handler contains its own throws, because a **synchronous** throw in one escapes `Promise.allSettled` and kills the Node process. `src/dev/bridge.test.ts` and `test/dev-session-lifetime.test.ts` hold both, plus the rule that `replace()` never settles the app's exit. Adding an error overlay, a terminal-ownership registry or JSX HMR are separate phases, deliberately absent rather than forgotten. **`pnpm dev` is that dev server** — there is one dev command (`tsx playground/dev.ts`; `vite-node` and `dev:hmr` are gone, and `vite-node` must not come back: it is retired upstream and its `--watch` never saw a `.vue` edit). The launcher exists because the entry cannot read `argv` — under the dev server `argv` belongs to `vite` — so `pnpm dev <name>` travels in `VUE_STDOUT_DEMO`, and `pnpm dev --list` is answered from `playground/catalog.ts` with no server at all. Because there is no ownership registry yet, **editing a Vite config while the dev server runs is undefined behaviour** — Vite builds the replacement server before closing the original, so two mounted apps briefly claim one terminal. That is documented, not fixed, in the README and in `playground/vite.config.ts`; do not describe it as safe. See [architecture](.agents/docs/architecture.md#the-dev-server), [technology stack](.agents/docs/technology-stack.md#vite-node-is-gone-pnpm-dev-is-the-dev-server) and [gotchas](.agents/docs/gotchas.md#a-synchronous-throw-in-a-vite-hot-listener-kills-the-process).
- `examples/cli-vite` deliberately stays on the stock `@vitejs` plugins. It is documentation, and what it documents is that a consumer inherits none of this package's compiler choices; it also acts as the live check that the shipped `dist/` never grows a dependency on the `unplugin-*` family. Do not "align" it with this package's config.
- **`createApp().mount()` is the only entry point**, and the object it returns is *Vue's own app* (`src/vueRenderer.ts` builds it; `src/createApp.ts` replaces `mount` and adds `waitUntilExit`). `render()`, `Instance` and `rerender()` are gone and must not come back — a Vue library does not ship a transliterated React entry point beside the Vue one. Anything added to the app object has to earn its place against that: `waitUntilExit()` is there because nothing inside the tree owns the app's lifetime, and `clear()` is deliberately *not*, because it needs the live `Container` and so belongs on `useStdout()`. **The exit promise is created in `createApp()`, never in `mount()`**: `teardownMount()` ends a mount and never settles it, `exitApp()` is the only path that does. That boundary is what lets HMR rebuild a mount without closing the dev server, and `test/dev-session-lifetime.test.ts` now holds it directly: break it and a full reload settles `waitUntilExit()`, which shuts the dev server down on the developer's first edit. Do not collapse it. `test/create-app.test.ts` and `test/create-app.test-d.ts` are the guards — every other test in the suite would pass against an app object that silently dropped `use`/`component`/`directive`/`provide`/`config`. See [architecture](.agents/docs/architecture.md#the-entry-point-createapp--mount).
- The host tags are `stdout-box` and `stdout-text`, and they are **private** — not exported, not typed for consumers, not augmented into `GlobalComponents` or `JSX.IntrinsicElements`. Authoring is the components (`<Box>`, `<Text>`, …). Adding a tag that is also a real HTML tag name is the specific mistake this arrangement exists to prevent; see [intent](.agents/docs/intent.md#non-goals).
- When code has to deviate from the obvious form because the situation requires it, say **why** in a comment. This package is full of such places — a wasm free-list hazard, a scheduler race, a deliberate ink divergence — and the next reader must not have to guess whether it was intentional. Comment density is watched, but the valve is redundancy, not reasoning: prune restatements of the code, keep arguments.
- Never write a `{@link}` to a symbol that is not exported. TSDoc blocks are copied verbatim into the built `.d.mts`, nothing in the toolchain validates link targets, and the dangling reference ships to consumers silently.
- ink is a live oracle, not a specification. Parity tests render the same tree through both engines and compare; ink's *code and observed output* are evidence, ink's *documentation* is not. See [ink reference](.agents/docs/ink-reference.md).
- Records live in `.agents/docs/`, and that is now the only prose. This package has **no `docs/` directory and no `CHANGELOG.md`** — the parity ledger, the four subproject ledgers, the subproject plans and specs, and the changelog were all deleted on 2026-08-31 at the owner's request. Do not recreate them, and do not link to them; the parity measurements live in the suite (`test/parity/**`, each divergence a registered case with its reasoning beside it), and the counts are derived by command — see [ink reference › The parity counts](.agents/docs/ink-reference.md#the-parity-counts-and-where-they-come-from). Note that the repository-root `docs/` is an unrelated thing — the published VitePress site — and is not covered by this.

## Project Context Records (PCR)

This project follows **Project Context Records (PCR)** — methodology: https://github.com/hyfdev/project-context-records. PCR keeps the project's durable judgment — the *why*, the decisions, the intent — so you inherit it instead of re-deriving or re-litigating what's already settled.

When working here:
- **Where records live.** Records are in `.agents/docs/`, one topic per file, cross-linked with relative Markdown links.
  - A `README.md` there is the **map**: it routes code areas or hotspots to the exact record or heading, one-line gist per route. Create it when retrieval stops being a glance or one record grows into a long ledger.
- **Read first.** Start from the map if present, else scan the folder. Open the records or headings that cover an area before changing or answering for it; if the area has a decision ledger, read it first.
- **Use the strongest durable form.** Machine-checkable constraints go in types, tests, lints, or CI; rules that must bind every session go in the agent-instructions file, outside the markers; single-spot rationale goes beside the code with a link; records carry the cross-cutting judgment, intent, and context that must stay prose.
- **Record as you go.** Capture context when a decision lands, a trap costs you, a human corrects you, or a human asks — anything true about this project, not durable in a stronger form, and useful beyond the moment.
  - Report what you record so a human can review or vouch it.
  - Records are as public as the repo: keep secrets out, and ask before recording rationale from private context.
- **Write to be acted on.** Lead with the current conclusion and where it applies; capture the why — trade-offs, alternatives rejected, known pitfalls. Keep each topic's current truth in one fresh place, updated in place: evolution belongs to git, never to supersede chains.
- **Keep it fresh.** Update affected records in the same change that touches their subject.
  - When code and a record disagree, decide which side went stale and fix that side.
  - Back facts with durable evidence — tests, reproducible commands, committed artifacts, stable URLs, commit hashes — not ephemeral paths or one session's output.
- **Provenance.** Unstamped text is AI-accumulated: challenge and verify it freely. `[VOUCHED @handle YYYY-MM-DD]` means the named human explicitly accepted the covered words as current project direction.
  - A vouch is direction, not proof: facts keep needing durable evidence. Don't reopen vouched direction for its own sake — only on new evidence, a changed constraint, or the human's say-so.
  - When evidence argues with vouched direction, record the conflict and surface it to a human; stay inside the direction unless progress becomes impossible. Silence is not an option.
  - Scope: at a non-heading line's end, the stamp covers that line; alone on the first nonblank line below a heading, that section until the next heading of the same or higher level; alone below the document title, the whole file. Never in heading text — link anchors derive from headings.
  - Add a stamp only on explicit instruction. A stamp added by work under review counts only once the named human confirms it; an unchanged stamp on the target branch is inherited project state.
  - The stamp binds the exact covered words. Any edit that changes them — or changes which words the scope covers — removes the stamp until the human re-vouches; a change that leaves the covered words identical keeps it.
  - Legacy stamp forms (undated, before the title, inside a heading) stay valid with their original scope; never move, re-date, or reinterpret one without the human's approval.
- **Decision ledgers.** When the human declares that an area records decisions, keep that area's judgments in `<area>-decisions.md` and register new judgments there.
  - Placement: beside the area's derived document (`DESIGN-decisions.md` beside `DESIGN.md`, typically both in the records folder); with no derived document, in the records folder — a map route either way.
  - You may propose opening a ledger; only the human opens one.
  - The register contract, stated at the top of the file: only judgments the human actually expressed enter — a finished implementation, a passed review, resemblance to a reference, or silence is not acceptance. Never invent a rationale: if no reason was given, the entry says so.
  - Record the act of judgment, not the chosen thing's full content — exhaustive detail lives in the area's own document, linked. Edit entries in place; git keeps history.
  - Entries sit under **Decided** or **Open**. An Open entry marks a known-undecided question — current behavior is not a choice — with any stopgap and what would settle it. A Decided entry carries:
    - a short stable topic heading — map routes and stamp scopes anchor to it;
    - **Ruling:** one plain sentence, its force in its own wording — must / never / prefer / default to; no status field;
    - **Limits:** what it does not govern, what may change without reopening it, what would reopen it — a stopgap is a ruling plus its reopen condition;
    - **Why:** premises, alternatives compared, rejections — exactly as the human gave them;
    - **Source:** who expressed it, when, a durable pointer; for "accept the reviewed thing as a whole", pin the thing (commit hash, spec section) instead of transcribing it;
    - the vouch stamp, once the human vouches the entry, alone under the entry's heading — covering the whole entry.
- **Distill when a human reviews.** Accumulation is noisy by design; the valve is a human pass, and you draft it.
  - Propose: prune what is contradicted or dead, merge near-duplicates, promote buried context, fix map drift. Unattended, apply this to your own unstamped layer as you go — never the vouched one.
  - Flag: unstamped direction that has become load-bearing, factual claims whose evidence no longer holds, vouches plausibly affected by changes to what they cover.
  - The human decides and vouches.
- **Suggested topics.** Draft the missing ones that apply; when an existing doc already covers a topic, enroll it — a map route pointing at it where it lives, held to these same rules — instead of drafting a twin:
  - `intent.md` — what this is trying to be, for whom, and the non-goals; enroll the README instead if it truly covers them.
  - `technology-stack.md` — why tools, restrictions, and pins exist; not a manifest dump.
  - `architecture.md` — units, boundaries, and why the lines are where they are; when structure isn't glanceable.
  - `gotchas.md` — traps already paid for, each with its why; only real paid lessons.
  - `DESIGN.md` — only for a visual surface; follow https://github.com/google-labs-code/design.md (records folder by default — the spec fixes no location), enroll it in the map, and suggest wiring its linter into the project's own checks with the file's actual path (e.g. `npx @google/design.md lint .agents/docs/DESIGN.md`; platform variants in the spec).
  - `loop-goal.md` — only for an unattended run: the run's contract — goal, boundaries, finish criteria. You may draft it; the run starts only once the human has vouched the whole file (stamp below the title), and a human edit plus re-vouch re-baselines it. Never edit it yourself; if the contract itself blocks progress, stop and surface the conflict rather than stepping outside it.
  - `loop-status.md` — only for an unattended run: the run's memory — done, in flight, next, blocked — overwritten in place each iteration; its final overwrite is the handover to the returning human (what landed, what to vouch, what to prune, conflicts included). Both `loop-*` files die after the human's distillation pass over that handover; git keeps them.
